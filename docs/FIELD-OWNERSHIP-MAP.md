# Field & engine ownership map

**Purpose: stop duplicates before they are written, cheaply.**

The frozen no-duplicate rule (one fact = one input = one destination = one
engine) is enforced by *knowing what already exists*, not by running tests. This
file is the lookup that makes that check take seconds instead of minutes.

**Use it like this — before adding ANY new field, column, service, engine,
endpoint, or UI input:**

1. Search this file for the fact you are about to store.
2. If it is listed → bind to the existing owner. Do not add a parallel field.
3. If it is genuinely absent → grep to confirm (`grep -rn "your_field" app/ database/migrations/`),
   add it, then **add a row here in the same commit**.

If this file and the code disagree, the code wins — and this file is stale and
must be fixed.

## 3. Duplicate traps that already bit us

Each of these was a real defect, not a hypothetical:

1. **Two gender inputs** on one wizard step, unlinked, writing the same column by
   two paths (2026-07-22). → One visible input; pass the value on.
2. **Invented "number of children"** where the reference flow uses repeatable
   rows (2026-07-22). → Mirror the reference flow exactly; do not design a
   "simpler" alternative.
3. **Gate removal deleted the field** — mother tongue stopped being collected
   when its gating behaviour was removed (2026-07-22).
4. **Contact fields accepted where no column exists** — silently dropped, later
   re-prohibited so clients get an honest 422 (2026-07-21 → 22).
5. **`user.email` used as the identity line** for OTP-registered Suchaks, so the
   admin list showed bare names (2026-07-23).
6. **Suspected-but-innocent:** `income_amount` vs `annual_income` looked like a
   duplicate and is not — one is derived from the other. *Check before
   "fixing".*
7. **A filter shipped for a value the surface hides — twice, in one slice
   (2026-08-03).** D7a added location and income filters to the cross-Suchak
   masked search. `whereResidenceUnderAncestor()` accepts an ancestor at any
   depth, so a **village id** sent as `district_id` narrowed the page to that
   village and read back the village D19a hides; and because no masked card
   prints an income at all, a **binary search over `income_min`** recovered an
   exact salary in 23 requests. Neither is a leak in the response body — both are
   leaks in the **result count**. Rule: adding a filter to a masked surface is a
   privacy decision, not a search decision. Ask what the card prints; if it does
   not print the value, the filter belongs on the own book only. Both attacks are
   now `SuchakCrossSearchOracleTest`.
8. **`suchak_plans` vs `suchak_customer_plans` — same word "plan", different
   meaning.** `suchak_plans` is the PLATFORM subscription catalog a Suchak *buys*
   (route `GET /suchak/plans`, `SuchakBillingApiController`, consumed live by
   Suchak-apk). `suchak_customer_plans` is the per-Suchak reusable presets a
   Suchak *sells* to their customers (route `/suchak/customer-plans`,
   `SuchakCustomerPlanService`). Never mount one on the other's route (the new
   resource is deliberately at `/customer-plans`, not `/plans`, to avoid
   shadowing the platform endpoint), and never reuse one model for the other.
9. **Never re-add `source_template_id` / `template_*` FKs or `*_json` stage
   columns to `suchak_service_package*`.** The reusable-plan "template" now lives
   in the separate, mutable `suchak_customer_plans` table and is materialized at
   send with NO back-FK. `SuchakServicePackage` stays immutable / admin-approved /
   per-customer. `SuchakPackageRateCardFoundationTest` guards those send-time
   tables — do not "link" the two models.
10. **`profile_matches` vs `suchak_match_suggestions` — both hold (profile,
   matched profile, score, reasons), and they are NOT interchangeable.**
   `profile_matches` is a *cache of the current answer*:
   `MatchingService::replacePersistedMatches()` wipes every row for a profile and
   re-inserts, so asking it "what did we already show this seeker last month" is
   always wrong — the evidence was deleted. `suchak_match_suggestions` is the
   *append-only history*: what was shown, when, with the frozen score/reason
   snapshot, plus the Suchak's decision. Never read history out of
   `profile_matches`, never bulk-delete `suchak_match_suggestions`, and never add
   decision columns to `profile_matches` (2026-07-26).
11. **The same 14 yonis existed twice, in two languages, both active**
    (2026-07-26). `master_yonis` held the Sanskrit set (`ashwa`, `gaja`, …) that
    `master_nakshatra_attributes` autofills from, **plus** an English set
    (`horse`, `elephant`, …) added later by a seeder. Both appeared in the
    dropdown, and `GunamilanService::YONI_ENEMY_PAIRS` was written in English —
    so the enemy-pair rule never fired on an autofilled profile, and the same
    animal under two spellings failed the `===` test. **4 of the 36 gunas were
    wrong on every autofilled profile.** Fixed by making Sanskrit canonical,
    remapping the FKs and deactivating the duplicates. A near-miss of the same
    shape: `keet` was missing from the Vashya pair table, so every Vrishchika
    pairing hit an undocumented 0.5 fallback.
12. **"No data" scored as "incompatible"** (2026-07-26). `calculate()` set
    `available` from the mere EXISTENCE of a `profile_horoscope_data` row, so a
    row of NULLs returned `available: true, total_points: 0/36` and a naive
    `>= 18` check called it INCOMPATIBLE — which would have excluded every
    member who never opened the horoscope step. A `computable` flag and a
    nullable `is_compatible` now separate "0 points" from "unknown". The same
    class of bug: the `other` rows on `master_gans` / `master_nadis` /
    `master_yonis` / `master_rashis` / `master_nakshatras` mean "did not know",
    so comparing two `other` nadis as equal invented a Nadi dosha out of
    nothing. `GunamilanMasterData::isComputableKey()` is the one place that
    decides a sentinel is absence, not a value.
13. **A threshold that drifted by one** (2026-07-26).
    `MobileProfileDisplayPresenter` tested `<= 18.0`, quietly making the
    owner's "18 of 36 is compatible" rule mean 19+. Thresholds live on
    `GunamilanService::COMPATIBLE_THRESHOLD`; do not re-type the literal.
14. **The score confirmed what the card hid — trap 7 a third time, through a
    different channel (2026-08-03).** Same response, same masked village: the
    fit explanation shipped beside the masked card resolved FINER than the card.
    `MatchingService::scoreLocationPart()` paid an exact `location_id` match the
    full location weight with the reason *"same city"* and a taluka-only match
    90% with *"same taluka"*, so one own candidate per village under the shown
    taluka, passed as `requesting_representation_id`, read D19a's hidden village
    out of `match_field_points['location']` — one request per guess, no counting.
    The same component leaked a second time through arithmetic:
    `reason_nearby_taluka` printed the kilometres, and
    `MatrimonyProfile::leafGeoBundle()` takes lat/lng from the LEAF, so three
    probes in a neighbouring district trilaterated the village position.
    **Rule: a masked surface's SCORE is part of the disclosure.** Whatever the
    filters may narrow by, the explanation may resolve by — no finer. Fixed by
    capping precision, never by deleting the signal (D19a: a matchmaker who
    cannot see enough cannot propose a match). The cap is a parameter on
    `computeMatchBreakdown()`; the DECISION to use it is taken only in
    `SuchakMatchFitService`, from `SuchakCandidateMaskingService::revealsVillage()`
    — the one reader of `shares_village`. The member path never reaches that
    class and keeps the exact tier (D19b). `SuchakCrossSearchOracleTest`.
15. **Two memos for one fact, and the second one keyed by the wrong thing
    (2026-08-03).** The cap in trap 14 held; the oracle failed anyway, but only
    when another test class had run first — four probes identical except for
    their village came back 53/53/55/55, and the difference was in
    `preferences`, not `location`. Cause: `ProfilePreferenceMatchService::$residenceGeoCache`
    and `MatchingService::$residenceGeoCache` each memoised "district / state /
    country / taluka of this profile" **keyed by PROFILE ID**, on top of
    `MatrimonyProfile::geoAddressIdsForLeaf()`, which already memoises the same
    walk keyed by `addresses.id`. The address key cannot go stale (an address's
    ancestry is master data); the profile key can, because a profile moves — and
    both memos were only ever cleared in `MatchingService::findMatchesForTab()`,
    the member-feed entry point, which the Suchak fit path never takes. So in
    any long-lived PHP process (queue worker, Octane; and in the suite, re-used
    profile ids across test classes) a candidate kept scoring against their OLD
    taluka. **Rule: memoise a fact under the key that fact actually depends on,
    and if a canonical memo for it already exists, delegate — a second memo is a
    second home.** Both were deleted in favour of the leaf-keyed one, and
    `$residenceDisplayCache` was re-keyed from profile id to `addresses.id` for
    the same reason. The oracle now warms the process deliberately (two probes
    scored once from another district, then moved back) so it fails under EVERY
    ordering rather than one. **Note what this was and was not:** the cached
    tuple stops at the taluka, so it could never name a village — what it
    produced was a fit explanation that depended on process history instead of
    on the pair, which is enough to make two masked candidates distinguishable.

15. **Two fail-open gates, both of which let a MARRIAGE claim stand on nothing
    (2026-08-04, blueprint §6.2 phase 4).** Neither was a missing rule; both were
    a rule placed where it did not run.
    (a) `SuchakCollaborationService::assertStageClaimant()` returned EARLY for
    `CLAIMANT_EITHER_SUCHAK` — **above** the "this engagement names no customer
    agreement revision" refusal. D26's *"either Suchak may raise the claim"* is
    about WHICH of the two may speak; it was being read as "and about nothing
    else". Every rung with a NARROWER claimant already passed through that
    refusal, so `meeting_scheduled` and the three TERMINAL rungs —
    `marriage_settled`, `engagement`, `marriage`, the ones that release the
    largest tranches in the system — were the **only** rungs exempt from it. A
    marriage could therefore be claimed on an engagement with no agreement
    revision, no frozen success fee, no tranche shares and `customer_owner_side`
    still on its column default: a §6.2 attribution with nothing to attribute.
    The refusal is now unconditional for every Suchak-claimable rung, which is
    what makes `suchak_marriage_outcomes.customer_agreement_id` NOT NULL
    possible — **the two are one change**.
    (b) `confirmationActorType()` mapped admin to `ACTOR_ADMIN`, threw for a
    participating Suchak's user, and let **every other authenticated user
    through** as `ACTOR_USER`. The check that actually protected it — "you must
    be one of the two candidates" — lived in `MemberSuchakStageApiController`.
    So the SERVICE's guarantee was "not a participating Suchak", and any second
    door onto `confirmStage()` would have let a stranger with a login settle a
    marriage claim worth tens of thousands. **The rule was MOVED into the
    service** (§12 forbids a second confirmation engine, and a rule enforced in a
    controller is a rule the next controller does not have); the controller's
    check stays as the **privacy** answer — 404, so a stranger never learns the
    engagement exists — rather than as the security boundary. Order matters and
    is unchanged: a participating Suchak is refused **first**, so a Suchak who is
    also a candidate on his own engagement cannot confirm his own claim.
    `SuchakMarriageOutcomeTest` pins both.

16. **A table with the right VOCABULARY and the wrong SHAPE — the near-duplicate
    that cost nothing only because it was checked first (2026-08-04, M2/M3).**
    `suchak_ledger_entries` reads like the cross-Suchak obligation: it already
    has `TYPE_SUCCESS_FEE_EXPECTED`, statuses `expected/due/paid/waived`, a
    `due_date`, a `paid_at` and even a `collaboration_request_id`. Every word
    the blueprint's money rules use is already in it. It still cannot express
    "Suchak A owes Suchak B", and no amount of vocabulary fixes that: it has ONE
    `suchak_account_id` and a **NOT NULL `matrimony_profile_id`**, so it is one
    Suchak's receivable against a PERSON. Adding `payer_suchak_account_id` would
    have (a) forced the married candidate into a column that then reads as "this
    family owes it", (b) rested a debtor/creditor pair on an `entry_type` a human
    picks from a `Rule::in` dropdown on two Blade forms — `CrmLedgerController`
    and `CollaborationController`, written by no engine — and (c) silently
    changed the meaning of every existing reader (the CRM ledger screen, both
    dashboards, `SuchakIncomeAnalyticsService`, `SuchakWorklistSourceQueries`),
    none of which filters on a column that did not exist when it was written.
    **Rule: matching vocabulary is not matching shape. Before reusing a table,
    read its NOT NULL columns and ask who writes its type — a row whose
    existence depends on somebody choosing the right string from a dropdown is a
    note, not an obligation.** The same check cleared three other candidates in
    one line each: `suchak_platform_payouts` (platform to ONE Suchak, no payer),
    `suchak_customer_payments` (customer to ONE Suchak, and no way to say WHICH
    fee) and `suchak_commission_agreements` (acceptance-only — pending/accepted/
    rejected/cancelled, with no due, paid or settled anywhere).
    `SuchakCrossSuchakObligationTest::test_no_existing_money_table_can_name_a_payer`
    pins all four as assertions, so the next "just add a column" trips over it.

## 4. The pre-flight check

Cheap (seconds). Never skip, even in fast mode:

```bash
grep -rn "the_field_name" app/ database/migrations/ resources/views/
```

Then state the result in one line before writing:
*"`X` already exists in `Y` — binding to it"* **or** *"`X` does not exist anywhere — adding it, map updated."*

Test suites are expensive and are skipped by default (see the Speed contract in
the workspace `CLAUDE.md`). **This grep is the cheap check and is not optional** —
it is what actually prevents duplicates.
